┌─────────────────────────────────────────────────────────────┐
│  1. SWAPCHAIN STABILITY  —  Tomb Raider (D3D11)            │
└─────────────────────────────────────────────────────────────┘

  Problem:
    Tomb Raider uses SwapEffect=DISCARD with BufferCount=2.
    The original code only created multiple backbuffers for
    flip-model swap effects (FLIP_DISCARD, FLIP_SEQUENTIAL),
    so DISCARD mode got BufferCount=1 regardless. This caused
    persistent "GetImage: Invalid buffer ID" errors (2813 per
    session) and eventual swapchain deadlock.

  Fix (commit 1346828):
    ─────────────────────────────────────────────────────
    Respect BufferCount >= 2 regardless of swap effect.
    ─────────────────────────────────────────────────────
    The backbuffer creation logic was changed to check
    BufferCount directly instead of the swap effect type.
    Now creates m_desc.BufferCount buffers when >= 2.

    Additionally, backbuffer swap is now atomic via a temp
    small_vector + std::move, preventing race conditions.

  Result:
    • 0 GetImage errors (was 2813)  ✅
    • Stable rendering through all game scenes
    • No swapchain deadlock on rapid scene transitions

  Affected file: src/d3d11/d3d11_swapchain.cpp
  Applicable to: All D3D11 games using DISCARD swap effect
                 (common in Unity, Unreal Engine 3 titles)


┌─────────────────────────────────────────────────────────────┐
│  2. SHADER PIPELINE STABILITY  —  General                  │
└─────────────────────────────────────────────────────────────┘

  2a. GPL + Async Pipeline Compilation
  ──────────────────────────────────────
  Problem:
    Graphics Pipeline Libraries (VK_EXT_graphics_pipeline_library)
    and async pipeline compilation (dxvk.enableAsync) are mutually
    incompatible. When both were active, GPL would eagerly compile
    pipelines that async was trying to defer, causing race
    conditions and driver crashes on Turnip.

  Fix (commit 1fe8861):
    ─────────────────────────────────────────────────────
    canUseGraphicsPipelineLibrary() returns false when
    dxvk.enableAsync is true.
    ─────────────────────────────────────────────────────

  Result:
    • No more GPL-vs-async race crashes
    • Async compilation works correctly when enabled
    • GPL works correctly when async is disabled


  2b. Zero-Init for Workgroup Memory
  ──────────────────────────────────
  Problem:
    Uninitialized shader workgroup memory causes GPU hangs on
    lower-end Adreno GPUs (6xx series) with Turnip. DXVK's
    zero-init mitigates this but costs ~1-2% shader performance.

  Fix (commit a8c994e):
    ─────────────────────────────────────────────────────
    shouldZeroInit() returns tier < 3.
      Tier 1/2 → zero-init ON (safety)
      Tier 3   → zero-init OFF (perf gain)
    ─────────────────────────────────────────────────────

  Result:
    • Tier 1/2: Stable, no GPU hangs from uninitialized memory
    • Tier 3: +1-2% shader performance
    • Graceful degradation if tiers are misclassified


┌─────────────────────────────────────────────────────────────┐
│  3. MEMORY & CACHE INTEGRITY  —  General                   │
└─────────────────────────────────────────────────────────────┘

  Problem:
    The shader cache writer thread used an indefinite wait
    (std::wait with no timeout). When Star Emulator / Winlator
    killed the process (SIGKILL), pending shader cache writes
    were lost, causing repeated cache misses and stutter on
    subsequent runs.

  Fix (commit a8c994e):
    ─────────────────────────────────────────────────────
    Writer thread uses 60s wait_for instead of indefinite wait.
    Drains all queued entries on timeout.
    Flushes on batch-full, shutdown, or timeout.
    ─────────────────────────────────────────────────────

  Result:
    • Shader cache survives emulator kill
    • Reduced pipeline compilation stutter across sessions
    • No cache corruption on unclean shutdown

  Affected file: src/dxvk/dxvk_shader_cache.cpp
  Applicable to: All games (universal fix)


┌─────────────────────────────────────────────────────────────┐
│  4. THREADING & CPU CONTENTION  —  General                 │
└─────────────────────────────────────────────────────────────┘

  Problem:
    Shader compiler threads were auto-detected via
    hardware_concurrency(), which on a typical 8-core big.LITTLE
    Android SoC spawns 8 compiler threads. These threads compete
    with the game's main thread and D3D11 render thread for CPU
    time, causing frame time spikes on the LITTLE cores.

  Fix (commit 5b7bcd5):
    ─────────────────────────────────────────────────────
    Cap auto-detected compiler threads to 4 on ARM64 (aarch64).
    User override via dxvk.numCompilerThreads is still respected.
    ─────────────────────────────────────────────────────
    Rationale: 4 threads is sufficient for parallel shader
    compilation. Beyond that, contention on the pipeline cache
    mutex and the CPU scheduler outweighs any benefit.

  Result:
    • Reduced CPU contention on big.LITTLE SoCs
    • More CPU time for main thread and render thread
    • Smoother frametimes during shader compilation
    • User retains full control via config override

  Affected file: src/dxvk/dxvk_pipemanager.cpp
  Applicable to: All ARM64 Android devices


┌─────────────────────────────────────────────────────────────┐
│  5. GOVERNOR & ADAPTIVE THRESHOLDS  —  Performance         │
└─────────────────────────────────────────────────────────────┘

  5a. TBDR-Safe Governor
  ──────────────────────
  Problem:
    The original governor had no upper cap on the draw threshold,
    allowing it to spike to 8000+ draws. On TBDR GPUs (Adreno),
    this causes tile-buffer overflow → spill to system memory →
    catastrophic performance collapse.

  Fix (commit a8c994e):
    ─────────────────────────────────────────────────────
    Capped max threshold at 2× base (was unbounded, 8000+).
    Added reset-to-base on moderate load.
    Reduced cooldown from 120 to 30 frames.
    Low-load path requires frameTime > 8ms.
    ─────────────────────────────────────────────────────

  Result:
    • No tile-buffer overflow on TBDR GPUs
    • Threshold resets prevent sticky high values
    • 4× faster governor response (120→30 frames)


  5b. Tier-Based Cap Multiplier (Bleeding-Edge)
  ────────────────────────────────────────────
  Problem:
    The uniform 2× cap was too conservative for high-end GPUs
    (Adreno 730+) and too aggressive for low-end (Adreno 610).
    One size does not fit all.

  Fix (commit 5b7bcd5):
    ─────────────────────────────────────────────────────
    Tier-based cap multipliers:
      Tier 1 (entry):    1.5× base — conservative, TBDR safety
      Tier 2 (mid):      2.5× base — balanced
      Tier 3 (high-end): 3.0× base — aggressive batching
    ─────────────────────────────────────────────────────

  Result:
    • Tier 1: Protected from tile overflow
    • Tier 2: More batching than before (+25%)
    • Tier 3: 50% more batching headroom (2.0× → 3.0×)
    • Each tier optimally tuned to its GPU's capabilities


  5c. Reduced Governor Cooldown (Bleeding-Edge)
  ──────────────────────────────────────────
  Problem:
    The 30-frame cooldown (~500ms at 60fps) was too slow to
    respond to sudden load changes (entering combat, cutscene
    transitions, new area loading).

  Fix (commit 5b7bcd5):
    ─────────────────────────────────────────────────────
    Cooldown reduced from 30 to 15 frames (~250ms at 60fps).
    EMA smoothing (0.9×prev + 0.1×current) prevents oscillation.
    ─────────────────────────────────────────────────────

  Result:
    • 2× faster governor response to load changes
    • Threshold adapts within ~250ms of a scene change
    • No oscillation due to EMA damping


  5d. Real GPU Load Estimate (Bleeding-Edge)
  ────────────────────────────────────────
  Problem:
    The governor's load input was hardcoded to 0.5f (always
    "moderate load"), which meant the "overheating" path and
    accurate GPU-bound detection were completely non-functional.
    The performance analysis could never return Overheating.

  Fix (commit 5b7bcd5):
    ─────────────────────────────────────────────────────
    GPU load is now estimated from the frame-time ratio:
      ftRatio = frameTime / targetFrameTime

      ftRatio > 2.0  → load = 0.96  (overheating)
      ftRatio > 1.5  → load = 0.92  (badly lagging)
      ftRatio > 1.2  → load = 0.85  (saturated)
      ftRatio > 0.9  → load = 0.65  (near capacity)
      ftRatio > 0.5  → load = 0.40  (some headroom)
      else            → load = 0.25  (lots of headroom)

    This real load is fed into both analyzePerformance() and
    tuneThreshold(), so the governor now makes decisions based
    on actual GPU utilization.
    ─────────────────────────────────────────────────────

  Result:
    • Overheating detection is now functional
    • Governor reacts proportionally to GPU load
    • Low-load games get aggressive batching (raise threshold)
    • High-load games get conservative batching (lower threshold)
    • Previously impossible: 6 distinct threshold states instead
      of binary "on/off"

  Affected file: src/dxgi/dxgi_swapchain.cpp
  Applicable to: All games (critical for governor correctness)


┌─────────────────────────────────────────────────────────────┐
│  6. GPU PACING  —  General                                 │
└─────────────────────────────────────────────────────────────┘

  Problem:
    The HAAE (Hardware Accelerated Adaptive Execution) thresholds
    were inverted: Tier 1 (Adreno 610) had the highest threshold
    (150 draws between empty submits), meaning the WEAKEST GPU
    got the LEAST frequent pacing. Tier 2 (mid-range) had the
    lowest threshold (65), getting the MOST pacing.

  Fix (commit 5b7bcd5):
    ─────────────────────────────────────────────────────
    Inverted HAAE threshold table to correct order:
      Tier 1 (low-end):   50 draws  — most frequent pacing
      Tier 2 (mid-range): 100 draws — moderate pacing
      Tier 3 (high-end):  150 draws — least frequent pacing
    ─────────────────────────────────────────────────────

  Result:
    • Tier 1: 3× more frequent GPU pacing (150→50)
      Prevents GPU overwhelm on Adreno 610
    • Tier 2: 35% less pacing (65→100), more throughput
    • Tier 3: 50% less pacing (100→150), maximum throughput
    • Correct inverse relationship: weakest GPU = most pacing

  Affected file: src/dxvk/dxvk_vegas.cpp
  Applicable to: All games (pacing affects all Adreno GPUs)


┌─────────────────────────────────────────────────────────────┐
│  7. TIER CLASSIFICATION  —  Compatibility                  │
└─────────────────────────────────────────────────────────────┘

  Problem:
    Tier classification relied on the upstream opaque function
    getStarEnginePersona() which was compiled into a prebuilt
    library, not source. It could not be modified or extended.

  Fix (commit a8c994e):
    ─────────────────────────────────────────────────────
    Replaced getStarEnginePersona() with custom classifyAdrenoTier()
    that parses GPU model from VkPhysicalDeviceProperties.deviceName.

    Mapping:
      5xx, 6xx < 620         → Tier 1 (entry)
      6xx 620-689, 7xx < 730 → Tier 2 (mid)
      690+, 7xx >= 730, 8xx+ → Tier 3 (high)
    ─────────────────────────────────────────────────────

    Added vegas.forceTier config option (0=auto, 1/2/3=override)
    for manual tier override.

  Result:
    • Transparent, modifiable tier logic (no opaque library)
    • Correct classification for all Adreno models
    • Manual override for edge cases or testing
    • Future-proof: new Adreno models can be added easily

  Affected files: src/dxvk/dxvk_vegas.cpp, src/dxvk/dxvk_options.h/.cpp
  Applicable to: All Adreno GPUs

┌─────────────────────────────────────────────────────────────┐
│  9. GPU BCn→ASTC TRANSCODER  —  release-v2 branch          │
└─────────────────────────────────────────────────────────────┘

  Problem:
    BCn-compressed textures (BC1–BC7) cannot be uploaded directly to
    ASTC-formatted Vulkan images. DXVK's `createImage()` swaps the
    image format to ASTC 4×4 on Adreno (where ASTC decode is available
    via Turnip), but the staging buffer still contains BCn data — the
    bytes must be transcoded before the upload copy.

    The original VEGAS CPU transcoder (`transcodeImageData()`) decoded
    BCn→RGBA8 on the CPU and re-encoded with a simplified ASTC encoder,
    taking 5.5–22 ms per mip/layer. It was never wired into the upload
    path because the CPU cost was prohibitive.

  Fix (Batches 1–5, commits 22d4ba5 → 19c9a86 on release-v2):
    ─────────────────────────────────────────────────────
    Replaced the gated CPU transcoder with an active two-pass GPU
    compute pipeline that runs on-device before upload:
      Pass 1: vegas_bcn_decode.comp — BCn→RGBA8 (scratch SSBO)
      Pass 2: astc_enc_leegao.comp  — RGBA8→ASTC 4×4 (PCA-based,
               2-partition mode support; LUTs from SSBOs)
    ─────────────────────────────────────────────────────

    Pipeline details:
    • Both shaders dispatch at ceil(w/4) × ceil(h/4) workgroups
    • Persistent RGBA8 scratch buffer (grow-only)
    • Independent submit + fence wait (Approach A — no DXVK state touched)
    • Lazy pipeline creation on first call

    Integration (3-file change):
    1. src/dxvk/dxvk_image.h — DxvkImageCreateInfo::originalFormat field
    2. src/dxvk/dxvk_device.cpp — createImage() swaps format if eligible
    3. src/d3d11/d3d11_initializer.cpp — transcodes after pack, before upload

    BC1/BC4 staging fix (Batch 5):
      BC1/BC4 use 8 B/block → ASTC 4×4 uses 16 B/block. The staging
      buffer must be allocated at 2× per-layer size so the transcoder
      output doesn't overflow into the next mip. Fixed by detecting
      elementSize < 16 and doubling the allocation + strides.

  Result:
    • All BC1–BC7 textures transcoded to ASTC 4×4 before GPU upload
    • ~0.15–0.26 ms per mip/layer (vs 5.5–22 ms CPU)
    • In-place staging for BC3/BC5/BC7 (same 16 B/block)
    • 2× staging for BC1/BC4 (8→16 B/block expansion)
    • Zero DXVK CS thread contention (independent submit)
    • Fail-safe: returns false on error, game continues

  Commits (in order):

    41bb85b  Step 2 — leegao's ASTC encoder SPV + LUTs
    fc06f55  Batch 1/5 — pipeline init (createStaticSsbo,
